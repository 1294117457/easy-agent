##### Memory、checkpoint的维护

```
graph中，
	有多个agent对应多个model，
	memory记录多个agent的操作，
	除了用户的输入，还有不同model的操作都清晰记录，
	后续回滚时也依具这个回滚
	
问题
	Memory如果全局的话，方便了整体graph的使用，
	但是单个agent调用时你觉得他需要维护一个自身的Conversation吗，
	还是说直接用全局Memory也读取到其他agent的记录呢，
	会不会混淆
解决
	记录还是都统一到Memory中，Memory中的每条记录有对应标识，区分不同agent，以及可能agent外的操作
	单个agent中不额外维护一个Conversation，依具自身标识从Memory中获取对应的记录，这样可以统一整体的回滚的同时，又避免不同agent间混淆

难点
	很考验Memory数据结构的设计，不然agent获取自身的记录时性能很差
	比如Memory设计一个链表或者数组，
	每条记录有自己的映射，比如map之类？agent通过映射提取自己的记录？
```

```
具体实现
	外层Vec<Record>，实现Memory全局插入顺序
	HashMap<AgentId,Vec<Record>>快速定位Agent独立记录
	额外还可实现时间索引、滑动窗口、GC、ID索引
```

LangGraph中

```
State
	记录了Memory公共数据、
	Messages共享消息、AgentContextsagent独立工作区，
	State才是整体流转的记录
Checkpoint是维护State的，
	每次checkpoint记录当前操作的增量和上一个checkpoint对吗
```

我想的

```
我想的是，比如prompt、skill、toll、mcp、外部api、用户画像，都是独立领域模型，并且是资源模型
这些资源模型可以设为共享，也可以独立给agent配备

state
	就是记录当前的整体的共享资源、每个agent的各自状态，比如有state.config是共享资源，state.agent[]是所有agent

Memory
	则是结合checkpoint，类似git一样，是整体graph流程的记录，内部维护就是所有操作(agent的聊天、工具调用、外部的hitl）和当时的state等等都是一个Record)都记录在Memory上
	每个agent就从Memory中提取自身的record独立维护context，类似@0609全局设想.md (36-37) 

然后checkpoint
	的作用就是回滚到对应的Memory节点时，整体的state就是直接恢复到当时的memory中的state，agent也是到对应Memory节点读取自己的context和当时的state中恢复自身的skill等，

整体就是Memory时全局的记录，记录内容有每一步的操作和对应的state
```

```
	Memory是整体Graph流程的维护，内部主要维护的是Record和State
	
	所有agent不用刻意维护自身情况，都是依赖Memory.State.AgentConfi维护自身；Memory.State.PublicConfig获取当时的全局资源，
	
	如果需要回溯，则是Memory进行回溯，所有agent的状态、上下文根据Memory自然也回溯

```

```
	不是在Memory.state中维护上下文，Memory.state只是整体的资源配置记录，
	比如Memory.state.publicConfig记录公共资源，Memory.state.AgentConfig[]，记录agent独立资源

	然后Memory.Record记录整体graph的操作，可能是用户输入/agent输出的对话，agent调用资源的操作、以及更多的操作

	然后Memory.Record是个Vec记录，同时还有HahsMap用于agent提取自身的context
```

```
Memory是主分支，内部agent都是从分支各自维护并且合并到主分支
Memory回滚，从分支则从主分支来回滚自身对吗
```



```
每个agent肯定都不能记录所有的上下文，上下文窗口肯定有大小限制
	这里就是每个agent内部维护一个滑动窗口索引数组，
	对话时依具索引数组，从Memory中提取当前上下文对吗，并且是不是可以增加一个上下文缓存，
	当到了窗口大小后，不仅更新索引窗口，同步只增减量更新上下文缓存，
	只有回溯的时候，从Memory.Record的hashMap<AgentId,Vec<AgentIndex[]>>恢复自身上下文索引，然后根据上下文索引恢复上下文缓存

	这样性能你觉得怎么样
```
